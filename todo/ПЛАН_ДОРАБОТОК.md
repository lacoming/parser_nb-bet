## Шаг A — Переработка Excel-вывода

**Суть:** Сейчас программа создаёт новый файл на каждый цикл с 4 листами.
Заказчик хочет: один файл на месяц, один лист, 18 колонок, дозапись после каждого цикла.

### A1. Новая единая модель строки (`src/excel/models.py`)

Удалить 4 отдельных dataclass:
- `ExcelRow` (29 колонок, лист «Проставленные»)
- `MissingRow` (12 колонок, лист «Ненайденные»)
- `RejectedRow` (14 колонок, лист «Отклонено»)
- `PendingRow` (12 колонок, лист «Ожидающие»)

Создать один `UnifiedRow` — 18 колонок по шаблону заказчика:

| # | Колонка | Описание |
|---|---------|----------|
| 1 | Дата | Дата матча (ДД.ММ.ГГГГ) |
| 2 | Время | Время матча (ЧЧ:ММ) |
| 3 | Лига | Название лиги |
| 4 | Дома | Хозяева |
| 5 | Гости | Гости |
| 6 | Ставка | Тип ставки (1, 2, X, 1X) |
| 7 | Kf1 старт | Стартовый кф на победу хозяев |
| 8 | KfX старт | Стартовый кф на ничью |
| 9 | Kf2 старт | Стартовый кф на победу гостей |
| 10 | KfNB | Кф NB-Bet по типу ставки |
| 11 | Мин KfKush | Минимальный нужный кф на Куше |
| 12 | Ставка на НБ | `+` или `-` — поставлен ли тип на NB-Bet |
| 13 | Ставка на Куш | `+` или `-` — поставлена ли ставка на Куше |
| 14 | основания для - на куше | Причина если не поставлено: `ratio` / `отсутствие` / `ожидание` |
| 15 | кф куша | Кф Куша при ставке или при ratio-отклонении |
| 16 | Дата ставки Куш | Дата постановки ставки на Куше (ДД.ММ.ГГГГ) |
| 17 | Время ставки Куш | Время постановки ставки на Куше (ЧЧ:ММ) |
| 18 | Ссылка | URL матча на NB-Bet |

Заполнение по сценарию:

| Сценарий | Ст. на НБ | Ст. на Куш | Основание | Кф Куша | Дата/Время Куш |
|----------|-----------|------------|-----------|---------|----------------|
| Ставка поставлена на Куше | +/- | `+` | — | кф | дата/время |
| Не найден на Куше | +/- | `-` | `отсутствие` | — | — |
| Ratio не прошёл | +/- | `-` | `ratio` | кф | — |
| Далёкое будущее (>2 дн.) | +/- | `-` | `ожидание` | — | — |

### A2. Обновить маппер колонок (`src/excel/default_mapper.py`)

Заменить `DEFAULT_COLUMNS` (29 колонок) на `UNIFIED_COLUMNS` (18 колонок) с шириной столбцов по шаблону заказчика.

### A3. Переписать `ExcelWriter` на openpyxl + месячная дозапись (`src/excel/writer.py`)

- Заменить библиотеку `xlsxwriter` → `openpyxl` (уже есть в зависимостях, поддерживает дозапись)
- Один буфер `_rows: list[UnifiedRow]` (вместо 4 отдельных)
- Имя файла: `ГГГГ-ММ_results.xlsx` (месячная ротация, например `2026-03_results.xlsx`)
- Логика `save()`:
  - Файл уже существует → открыть, найти последнюю строку, дописать новые строки
  - Файл не существует → создать, записать заголовок, записать строки
  - Один лист «Результаты»
- Убрать методы `add_missing_row()`, `add_rejected_row()`, `add_pending_row()` — остаётся один `add_row(UnifiedRow)`
- Убрать свойства `missing_count`, `rejected_count`, `pending_count` — оставить только `row_count`
- После перехода — удалить `xlsxwriter` из `requirements.txt` (экономия ~0.4 МБ в exe)

### A4. Обновить цикл (`src/scheduler/cycle_runner.py`)

Все 4 ветки обработки матчей теперь создают `UnifiedRow` вместо разных моделей.
`nb_placed` определяется через `state.is_nb_placed(match_key)` в момент формирования строки.

### A5. Обновить тесты (`tests/test_excel.py`, `tests/test_e2e.py`)

- Заменить все ссылки на старые 4 модели → `UnifiedRow`
- Проверить: 18 колонок, 1 лист
- Добавить тест append: записать → закрыть → дописать → проверить объединённые строки

## Шаг B — Фикс НБ-ставок + Telegram

### B1. Баг: НБ-тип не ставится для «ожидающих на Куше» матчей (`src/scheduler/cycle_runner.py`)

**Текущее поведение:** Stage 3b (размещение тип на NB-Bet) запускается только на `passing` — список near-window матчей. Far-future матчи (>2 дней) вообще не получают тип на NB-Bet.

**Исправление:** Собрать все решённые матчи (near + far) в общий список `all_decided`, запускать NB placement на нём.

### B2. Telegram: дедупликация уведомлений (`src/state.py`)

## Шаг C — Стабильность запуска (по жалобе заказчика)

**Проблема:** Заказчик не может редактировать `config.json` и `leagues.xlsx` — после изменений программа «не запускается и выдаёт ошибку». Использует сложный обходной путь с тремя запусками.

**Причины (диагноз):**
1. При ошибке в `config.json` (неправильный JSON-синтаксис) программа падает до открытия UI — заказчик видит ничего или мигающее окно
2. Файлы результатов (`2026-03-01_results.xlsx`) могут подхватываться как `leagues.xlsx` если лежат рядом
3. Лиги загружаются один раз при старте — изменения в `leagues.xlsx` требуют перезапуска (этого заказчик не знает)

### C1. Понятное сообщение об ошибке конфига (`src/main.py`)

Обернуть `load_config()` в `try/except`, при ошибке показывать `messagebox.showerror()` с конкретным текстом:
```
Ошибка конфигурации
config.json: строка 12 — ожидалась запятая
```
Не падать молча.

### C2. Исключить файлы результатов из поиска лиг (`src/decision/league_loader.py`)

В `find_leagues_xlsx()` добавить паттерн `^\d{4}-` в список исключений — файлы вида `2026-03-01_results.xlsx` не будут приниматься за leagues-файл.

### C3. Hot-reload лиг каждый цикл (`src/scheduler/cycle_runner.py`)

Перечитывать `leagues.xlsx` в начале каждого цикла, а не только при старте. Заказчик может менять состав лиг — изменения вступят в силу на следующем цикле без перезапуска программы.
